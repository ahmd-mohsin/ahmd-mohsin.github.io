Quick start
Agentic RL for enterprises

Crucible

Your work goes in. Trainable RL environments come out.

Your teams make expert decisions every day. They review, correct, test and approve work. Crucible records this work and makes RL environments from it. Each environment scores each step, gives tasks that frontier models fail and comes with a benchmark.

The problem

Real agent work happens inside enterprises

Today, experts make RL environments by hand. They find tasks where models fail and build an environment for each task. Then they train a model, test it on a benchmark and sell the environment or its data. This method has limits.

There are not enough expertsEach environment needs expert time. The work is slow and difficult. Labs now reach the limit of this method.
Real work crosses departmentsMost environments cover one domain, for example code. Enterprise work is horizontal. Finance, HR, sales and engineering often work on one report.
Each enterprise has thousands of workflowsThese workflows are long and dense. It is very difficult to build them by hand, and it is also difficult to measure them.
The data stays insideEach enterprise has its own data and its own workflows. This data never goes out of the enterprise. An environment made outside cannot copy these workflows.
Our answer

A black box that turns enterprise work into RL environments

Crucible runs inside the enterprise. It reads the agent traces and the expert feedback in your workflows. It makes RL environments from them, with rubrics that give a strong signal at each step. You use these environments to train your own open models on your own workflows. Crucible also makes the benchmark that measures the improvement.

The difficult part is the expert signal. A weak signal teaches the model from low quality, AI made data. Crucible keeps each signal grounded in what your experts really did. Then a model helps to improve a model, and the loop continues. We will use Crucible to make many more enterprise environments.

The rules

The model proposes. The record decides.

Score the resultThe reward measures the state of the work, not the keys that the agent pressed.
No points for loopsIf the agent breaks a thing and fixes it again, it gets no reward.
Rules come firstIf the agent breaks a hard rule, the episode gets zero.
System faults do not countIf the system fails, Crucible marks the run. It does not score it as zero.
The environment enforces the rulesThe rules live in the environment and its checks, not in a prompt.
One base, many domainsEach domain plugs in as a pack. The base stays the same for all domains.

The Crucible world

A real workplace, inside a safe sandbox

A Crucible world is a running copy of a workplace. It holds apps, people, a clock and events. The agent works in it the way a person works at a desk. Hidden checks read the result. Crucible can save and restore the full world at any step.

Drag to turn

What a world can hold
  • Databases, from a small file to a full database server
  • Files and code with their full history
  • Documents, spreadsheets, slides and PDF files
  • Inboxes and message threads
  • Websites and a real browser
  • A hidden check runner and GPU tools
  • Any tool server that uses the standard tool protocol
Where a world runs
  • On this machine, for fast tests
  • In a container on this machine
  • In a container on a remote GPU host
  • In a cloud sandbox, with the GPU type that you ask for
  • A snapshot from one place restores in another place
How time works
  • Step time moves one tick for each action
  • Wall time moves at a set speed and stops when the world pauses
  • Simulation time moves only when the simulator moves it
  • Events occur at a set time or after a set action
  • Tools read the world clock and the world seed, so a replay gives the same data
What keeps it safe
  • The agent gets a new account with few permissions
  • Programs that raise permissions do not work for the agent
  • The network is closed, and a self test proves it before the first step
  • The checks use their own trusted copy of the code history
  • Crucible stops leftover processes and cleans temporary files between episodes
  • A suite of more than 20 attacks runs against the sandbox
How the gate checks each action
  • It checks the tool name and the permission of the actor
  • It checks the inputs against the format of the tool
  • It stops a tool that runs too long
  • It limits the size of the output
  • It counts calls against a budget for each tool
  • If an app fails, the gate holds the error and the episode continues
Why it is generic
  • The base has no domain logic. All domain parts come from packs.
  • Any app that has state and tools can join a world
  • Each app gives a fingerprint, a snapshot and a restore
  • A world can end itself, return images and use its own seed for each app
  • An audit command checks any world before you use it
RL infrastructure

How Crucible trains a model while agents work

Crucible has its own RL infrastructure. Agents collect data in live worlds while the trainer updates the model. Each part has one job and one clear contract.

Drag to turn

Worlds and episodes
  • Each episode runs as its own task
  • Worker machines run the worlds, with leases and heartbeats
  • Environment servers keep one live session for each episode
  • A slow world never blocks the batch
Models
  • Inference engines run behind one gateway
  • Each episode stays on the same engine
  • A failed engine leaves the pool, and its calls start again on another engine
  • Each reply carries the model version that made it
Records
  • Crucible keeps the exact tokens that the model made, and never tokenizes the text again
  • Each token keeps its probability and its model version
  • Each record keeps the step scores and the cause of each failure
  • A masked record never goes into training
Scheduler
  • It admits new work only when the trainer can use it
  • It picks each batch by groups of tries
  • It drops data that is older than the limit
  • One run can mix many domains, each with its own age limit
Dense reward
  • Milestones come from real expert work
  • Progress is the share of milestones that are complete
  • Each step earns its change in progress
  • Each step score goes onto the tokens of its turn
  • The group of tries gives the baseline for each advantage
  • A broken rule gives zero, and loops earn nothing
Training and weights
  • The trainer corrects each token for the age of its data
  • It supports group advantages, a critic over segments and learning from a teacher model
  • New weights reach all engines in one step
  • Three layouts are available. One shared GPU, partly shared GPUs, or separate machines.
  • One command starts the engines, the workers, the environment servers and the trainer
Long episodes
  • A summary starts a new segment, and the trainer learns from the summary
  • Credit crosses from one segment to the next
  • Save points let a crashed episode continue
Hack defense
  • A check stops dangerous calls before they run
  • It flags episodes that change tests or fake an exit status
  • A judge looks only at flagged episodes
  • A confirmed hack gets no reward
Long tasks

How we build tasks that take a full shift

Real enterprise work runs for hours. Crucible builds long tasks from real cases and keeps the reward dense and exact from the first step to the last.

Drag to turn

Grow one case into a shift
  • Crucible takes a real case and makes many related cases
  • Each case has its own data, people and correct result
Make the agent wait
  • Some replies arrive hours later in world time
  • The agent must come back to the case
Change a rule
  • A rule changes during the shift
  • The checks score each action by the rule in force at that moment
Link the cases
  • Later cases refer to earlier cases, for example the same order
  • The agent must stay consistent across hundreds of steps
Add real context
  • Message threads and knowledge base documents fill the context
  • The model must summarize to continue
Keep approvals honest
  • A simulated approver must approve the exact amount
  • The approval must occur inside the episode
Summarize and continue
  • Near the context limit, the model writes its own summary
  • A new segment starts, and the trainer learns from the summary too
Save and resume
  • The world, the model state and the progress save together every few steps
  • A crash continues from the last save, not from the start

Foundation

One record format, a simulated workplace, and people who say only what is on record

Shared records

One record format for all parts

All parts of Crucible use it. Bad records do not get in.

Drag to turn

Crucible keeps worlds, work records, feedback, milestones, rewards, tasks and runs as versioned records. Each record has a content hash. The base holds no domain logic.

  • Strict format. Crucible rejects unknown fields and wrong versions.
  • Safe storage. Crucible finds damaged records when it reads them.
  • Clear source. Each record names the records it came from.
  • Pack registry. Packs add themselves. The base does not depend on them.
Simulated workplace

A live workplace that you can rewind

Apps, people, a clock and exact snapshots.

Drag to turn

Crucible makes a running workplace from a spec. Databases, documents, inboxes and workspaces become apps. People become simulated people. Events occur on a world clock. The agent acts in this world. Hidden checks read it through a view that the agent cannot see.

$ crucible world validate world.yaml --gold actions.json
  • One gate for actions. Crucible checks and limits each tool call.
  • Exact rewind. A fingerprint of each app proves the restore.
  • Locked sandbox. The agent cannot get out to the network.
  • World clock. Replies and rule changes occur on world time, so runs repeat exactly.
Simulated people

People who answer from the record

Customers, reviewers and approvers who do not make things up.

Drag to turn

All people other than the agent live inside the world. They reply only with what real people wrote. If there is no record, they say “I have no record of that.”

  • Quote mode. The model selects a reply. The record gives the words.
  • No future data. Records stay hidden until their time.
  • Checked facts. Numbers and dates must match exactly.
  • Real reviewers. Crucible replays real review comments at the matching code.
Understand work

Record what experts did, find their feedback and map the workflow

Work capture

Record real work and remove secrets first

Many sources go in. One record format comes out.

Drag to turn

Crucible reads ticket and ERP exports, audit logs, model traffic, code history, test reports and policy documents. It turns them into one record format. It removes secrets before it stores anything.

$ crucible ingest my_pack
  • Secrets out first. Crucible replaces each secret with a stable alias.
  • No change to your tools. A recording proxy watches live agents.
  • Same input, same result. A second import gives identical records.
  • Answer lookups marked. Crucible marks lookups of the answer key and does not score them.
Expert feedback

Expert judgement is already in your logs

Corrections, approvals and reverts become scored evidence.

Drag to turn

Crucible finds expert feedback in the records. It links each item to the step that it judges. It gives more weight to feedback that predicts what happens next.

$ crucible signals my_pack
  • 13 feedback types. Each domain maps onto the same 13 types.
  • Feedback follows changes. Crucible links feedback to the last step that changed the item.
  • Learned trust. Crucible gives less weight to weak feedback.
  • Before and after pairs. Each corrected error becomes a wrong and fixed pair.
Workflow map

The shape of the job

Crucible learns the stages and milestones from real work.

Drag to turn

Crucible splits each record into steps and rebuilds the state after each step. It finds milestones that it can check in changes, test results and reviews. A tracker tells an agent how far it is.

$ crucible model my_pack
  • Replay test. The rebuilt state must match the record.
  • Real milestones. Each milestone is a check that runs and predicts success.
  • Stages from data. “A before B” must occur in 90% of records or more.
  • No guesses. Crucible sets aside records that do not replay.
Reward

A score at each step that agents cannot cheat, from checks that agents cannot touch

Step scores

A score at each step

Progress that you can measure and that agents cannot farm.

Drag to turn

Progress is the weighted share of milestones that the agent completed. A milestone counts only when its earlier milestones are also complete. Each step earns the change in progress. Rules and a cap keep partial work below full success.

reward  R = G · [ O·(1 + αp + βe) + κ·(1 − O)·Φ ]    κ ≤ 0.3
  • Fair shaping. Loops give zero net progress.
  • Rules first. One broken rule gives zero.
  • Capped partial credit. Partial work always scores below success.
  • Branch values. Crucible estimates them from restored snapshots.
Result checks

Checks behind glass

Hidden, isolated and tested against each known cheat.

Drag to turn

The checks run in a separate container with no network. They trust only evidence that the agent cannot write. They compare the results with hidden references. They do not trust exit codes or claims.

  • Safe evidence. The checks use only evidence that the agent cannot forge.
  • Hidden references. Hidden answers and new samples catch fake results.
  • Fair timing. Crucible marks noisy runs and does not fail them.
  • Cheat tests. Control runs prove that each defense works.
Make tasks

Build new tasks from the solution first, and accept them only with proof

Task builder

Tasks that frontier models fail

A team of AI roles with walls between them.

Drag to turn

Special roles turn work records into new worlds and tasks. The solution and the hidden checks exist before an agent tries the task. Each role sees only the inputs that it needs.

$ crucible forge my_pack
  • Solution first. The solution and the checks come before each attempt.
  • Leak marker. If a role leaks the solution marker, that role fails.
  • Traps from real errors. Each trap comes from real expert feedback.
  • Correct difficulty. Crucible aims for a training pass rate from 0.1 to 0.7.
Quality gate

No proof, no task

Eighteen checks stand between a task and the task pool.

Drag to turn

The gate proves that the solution passes and that empty attempts fail. It proves that the checks catch planted errors, that no answer leaks and that the checks resist attacks. No model decides a gate. Each new error type becomes a new check.

$ crucible accept my_pack
  • Low cost first. Fast checks run first. People check last.
  • Catch 90% or more. The checks must catch planted errors.
  • Only changes again. An edit checks again only the parts that it changed.
  • A growing list. Each new check runs on all tasks again.
Run and learn

Run agents, train models and keep the context of long tasks

Agent runs

System faults never count as agent failures

Many tries, any agent, a cause for each failure.

Drag to turn

Crucible runs each task with each agent many times. It uses budgets, retries and a run log, so a run can continue after a stop. It removes system faults from all averages. It scores agent faults.

  • A cause for each failure. System faults stay out. Agent faults count.
  • Safe spending. Crucible reserves the budget before each attempt and settles it after.
  • Continue from any point. Crucible does not run finished work again.
  • Score again from results. Crucible scores a run again without a new agent run.
Model training

Train while the agents work

Agents collect data and the model learns at the same time.

Drag to turn

Agents act in live worlds while the model updates. Each token keeps the model version that made it. Crucible limits the age of the data at three points.

$ crucible train job.toml
  • Exact tokens. Crucible trains on the exact tokens that the model made.
  • Three layouts. One shared GPU, partly shared GPUs, or separate machines.
  • Corrections for old data. Crucible changes the weight of each token for its age.
  • A score for each turn. The step scores go onto the tokens of each turn.
Long tasks

A million tokens in one task

Summarize, save, crash, continue, and the score still adds up.

Drag to turn

One task can take thousands of steps. Near the context limit, the model writes its own summary and starts a new segment. The world saves its state every few steps, so a crash continues from the last save.

  • Own summaries. The model writes a summary at 80% of the limit.
  • Segments. Each summary starts a new segment that Crucible trains.
  • Exact total. The step scores add up to the final reward.
  • Small storage. Crucible stores only the new tokens of each step.
Memory agent

The agent keeps its memory in code

A short prompt over a memory that does not forget.

Drag to turn

The task, the tools, each observation and each message are variables in a sandboxed memory. The model reads them when it writes code. It sends questions to helper models. Crucible keeps old turns word for word, and the model can still search them.

  • Prompt as variables. Task, tools, observations, messages and history.
  • One step for each call. Each world call is one world step.
  • Helpers get credit. Helper calls share the credit of the call that made them.
  • Exact restore. Crucible replays the memory log and checks it.
Task repair

Tasks that repair themselves

Plan, change, review, check, and only then save.

Drag to turn

The memory agent also runs a loop that repairs and improves tasks. A different model reviews each change. The quality gate, not a model, makes the last decision.

  • Hard review. A second model looks for errors.
  • Objective check. The quality gate decides, not an opinion.
  • No weaker checks. A change can only make the checks stronger.
  • Run log. A stopped loop continues from where it stopped.
Measure and ship

Find where agents fail, and add new domains

Benchmarks

Where agents fail, step by step

Progress, not only pass or fail.

Drag to turn

Crucible benchmarks show which rules agents break, how far and how fast they get, what got worse and what it cost. Fixed items and new items share one scale. Thus you can compare versions, and old answers do not help.

$ crucible bench run finance_ap --out runs
  • Fair averages. Removed runs never count as samples.
  • Fixed and new items. Secret seeds make the new items.
  • One scale. Crucible puts models and items on one scale.
  • Paired tests. Crucible compares two versions on the same items.
Replay and export

One task, one reward

Each run replays into the same reward and step files.

Drag to turn

Crucible turns a recorded run into standard actions and replays them in a new world. One scorer scores the replay. The reward and step files are identical each time. You can use them for training or for audit.

$ crucible export --to canonical --pack finance_ap
  • Standard actions. Crucible makes its own action IDs and does not trust the record.
  • New replay. The actions run again in a new world.
  • Same files. Each replay gives the same reward file.
  • Marks stay. Crucible never writes a removed run as zero.
Domain packs

Add a new domain

One file describes a domain. The base stays the same.

Drag to turn

A pack holds all parts that are specific to a domain. These are sources, scoring rules, task makers, agents and test cases. Crucible checks each pack at three levels before it uses it.

$ crucible pack new my_pack --dir ./my_pack
$ crucible pack check ./my_pack --level semantic
  • Structure check. Crucible checks the manifest, license, layout and hooks.
  • Test cases. Each designed case gets the expected score.
  • Meaning check. The solution gets the top score. An untouched task does not.
  • Accounts payable. A three-way match with five fraud controls.

Quick start

        
No model, no GPU, no API key.

        
All steps run on a laptop CPU in about two minutes. Each command shows the next command.

      

      
# make a domain pack and check it at all levels
$ crucible pack new my_pack --dir ./my_pack
$ crucible pack check ./my_pack --level semantic

# turn logs into scored records and training data
$ crucible label --pack my_pack --out label

# turn logs into accepted tasks and a benchmark report
$ crucible build my_pack --out build

# run a real domain, accounts payable
$ crucible bench run finance_ap --out runs
