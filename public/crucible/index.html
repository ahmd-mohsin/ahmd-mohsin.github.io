Quick start
Agentic RL for enterprises

Crucible

Reinforcement learning environments constructed from enterprise workflow records.

Enterprise teams make expert decisions during their work. They review, correct, test and approve outputs. Crucible records these decisions and constructs RL environments from them. Each environment provides step-level reward, tasks on which frontier models fail and a benchmark.

Motivation

Agentic work occurs inside the enterprise

Domain experts currently construct RL environments by hand. They identify tasks on which models fail and build one environment for each task. They then train a model and evaluate it on a benchmark. This procedure has four limitations.

Limited expert supplyEach environment requires expert time. Construction is slow and difficult, and current methods approach their limit.
Horizontal workflowsMost environments cover a single domain. Enterprise work is horizontal. Finance, human resources, sales and engineering frequently contribute to a single output.
Workflow scaleEach enterprise operates thousands of long, dense workflows. Manual construction and evaluation of these workflows does not scale.
Data localityEnterprise data and workflows remain inside the enterprise. An externally constructed environment cannot reproduce them.
Approach

An in-enterprise system that converts workflow records into RL environments

Crucible operates inside the enterprise. It reads agent traces and expert feedback from existing workflows and constructs RL environments from them. Rubrics in each environment provide a strong signal at each step. The enterprise trains its own open models on its own workflows with these environments. Crucible also constructs the benchmark that measures the resulting improvement.

The main difficulty is the accuracy of the expert signal. A weak signal trains the model on low quality synthetic data. Crucible grounds each signal in recorded expert decisions. In this system, one model improves another. The same system constructs further enterprise environments.

Design principles

Reward follows recorded outcomes

State-based rewardThe reward depends on the resulting state of the environment, not on the sequence of actions.
Progress-based shapingThe shaping terms cancel over an episode. An action that the agent undoes and then repeats yields zero net reward.
Hard constraintsA violation of a hard constraint sets the episode reward to zero.
Masking of infrastructure faultsAn infrastructure failure masks the episode. Averages and training exclude masked episodes.
Environment-side enforcementThe environment and its checks enforce the constraints, not the prompt.
Domain-agnostic corePacks supply all domain-specific components. The core remains identical across domains.

The Crucible world

An executable workplace within an isolated sandbox

A Crucible world is an executable model of a workplace. It contains applications, simulated people, a clock and scheduled events. The agent interacts with it through tool calls, and hidden checks inspect the resulting state. Crucible can save and restore the complete world at any step.

Drag to turn

Supported applications
  • Databases, from a small file to a full database server
  • Files and code with their full history
  • Documents, spreadsheets, slides and PDF files
  • Inboxes and message threads
  • Websites and a headless browser
  • A hidden verification runner and GPU toolchains
  • Any tool server that the agent can call
Execution backends
  • The local machine, for fast iteration
  • A local container
  • A container on a remote GPU host
  • A cloud sandbox with a specified GPU class
  • A snapshot from one backend restores on another
Time models
  • Step time advances one tick per action
  • Wall time advances at a configurable rate and stops while the world pauses
  • Simulation time advances only under the control of the simulator
  • Events trigger at a scheduled time or after a specified action
  • Tools read the world clock and seed, which makes replay deterministic
Isolation
  • The agent receives a new account with minimal privileges
  • The sandbox disables privilege escalation for the agent
  • The sandbox closes the network, and a self-test confirms this before the first step
  • The checks use a trusted copy of the version history
  • Crucible removes residual processes and temporary files between episodes
  • A suite of known attacks tests the sandbox
Action validation
  • It verifies the tool name and the permissions of the actor
  • It validates the arguments against the tool schema
  • It enforces a time limit on each call
  • It bounds the size of the output
  • It enforces a call budget for each tool
  • It contains application failures, and the episode continues
Generality
  • The core contains no domain logic. Packs supply all domain components.
  • Any application with state and tools can join a world
  • Each application provides a fingerprint, a snapshot and a restore operation
  • Worlds support self-termination, image observations and per-application seeds
  • An audit command validates any world before use
RL infrastructure

Asynchronous training on live environments

Crucible includes its own RL infrastructure. Rollout collection in live worlds proceeds concurrently with policy updates. Each component has a single responsibility and a defined contract.

Drag to turn

Rollouts
  • Each episode executes as an independent task
  • Worker machines run the worlds under leases with heartbeats
  • Environment servers maintain one session per episode
  • A slow environment does not block the batch
Inference
  • Inference engines operate behind a single gateway
  • The gateway routes each episode to a fixed engine
  • The gateway removes a failed engine from the pool and reissues its requests
  • Each response records the policy version that produced it
Rollout records
  • Crucible stores the exact sampled tokens and never retokenizes text
  • Each token records its log probability and policy version
  • Each record stores the step rewards and the cause of any failure
  • Training excludes masked records
Scheduler
  • It admits new rollouts only when the trainer can consume them
  • It forms batches from complete groups
  • It evicts data beyond the staleness limit
  • A single run can mix domains, each with its own staleness limit
Dense reward
  • Milestones derive from recorded expert work
  • Progress is the weighted fraction of completed milestones
  • Each step receives the change in progress
  • Crucible assigns each step reward to the tokens of its turn
  • Other attempts at the same task provide the baseline for each advantage
  • A constraint violation yields zero reward, and cycles yield zero net reward
Training and weights
  • The trainer applies an importance correction for the staleness of each token
  • It supports advantages measured against other attempts at the same task, a value model over segments and distillation from a teacher model
  • The trainer publishes weights to all engines atomically
  • Training and inference share one GPU, share part of the GPUs or run on separate machines
  • A single command launches the engines, workers, environment servers and trainer
Long episodes
  • Each summary opens a new segment, and training includes the summary
  • Credit propagates across segments
  • Checkpoints allow an interrupted episode to resume
Reward-hacking defense
  • The environment intercepts dangerous calls before execution
  • A detector flags episodes that modify tests or forge an exit status
  • A judge reviews only flagged episodes
  • Confirmed hacks receive zero reward
Long tasks

Construction of long-horizon tasks

Enterprise work spans hours. Crucible constructs long-horizon tasks from recorded cases and preserves dense, exact reward from the first step to the last.

Drag to turn

Case expansion
  • Crucible expands a recorded case into many related cases
  • Each case has its own data, actors and reference outcome
Delayed dependencies
  • Some replies arrive hours later in world time
  • The agent must return to the case
Non-stationary rules
  • A policy rule changes during the episode
  • The checks evaluate each action under the rule in force at that time
Cross-case dependencies
  • Later cases reference earlier cases, for example the same order
  • The agent must remain consistent over hundreds of steps
Context pressure
  • Message threads and knowledge base documents accumulate in context
  • The model must summarize to proceed
Grounded approvals
  • A simulated approver must approve the exact amount
  • The approval must occur within the episode
Self-summarization
  • Near the context limit, the model writes its own summary
  • A new segment begins, and training includes the summary
Checkpointing
  • Crucible checkpoints the world, the policy state and the progress together at fixed intervals
  • An interrupted episode resumes from the last checkpoint

Foundation

A unified schema, executable worlds and grounded actors

Shared records

A unified record schema

All components share one versioned schema, which rejects invalid records.

Drag to turn

Crucible keeps worlds, work records, feedback, milestones, rewards, tasks and runs as versioned records. Each record has a content hash. The base holds no domain logic.

  • Strict validation. Crucible rejects unknown fields and incorrect versions.
  • Integrity checks. Crucible detects corrupted records on read.
  • Provenance. Each record identifies its sources.
  • Plugin registry. Packs register themselves, and the core has no dependency on them.
Simulated workplace

An executable workplace with exact restore

Applications, simulated people, a clock and exact snapshots.

Drag to turn

Crucible starts a running workplace from a specification. Databases, documents, inboxes and workspaces become applications, and people become simulated actors. Events occur on a world clock. The agent acts in this world, and hidden checks read it through a view that the agent cannot access.

$ crucible world validate world.yaml --gold actions.json
  • Single action gateway. Crucible validates and bounds each tool call.
  • Exact restore. Application fingerprints verify each restore.
  • Network isolation. The agent has no network access.
  • World clock. Replies and rule changes occur in world time, which makes runs reproducible.
Simulated people

Actors grounded in recorded data

Customers, reviewers and approvers that respond only from records.

Drag to turn

All participants other than the agent reside inside the world. They respond only with text that real people wrote. In the absence of a record, they reply “I have no record of that.”

  • Quote mode. The model selects a reply, and the record supplies its content.
  • Temporal masking. Records remain hidden until their timestamp.
  • Citation verification. Numbers and dates must match the source exactly.
  • Recorded reviewers. Crucible replays real review comments at the corresponding code.
Understand work

Trace capture, expert signals and workflow modeling

Work capture

Trace capture with redaction before storage

Many kinds of sources map to one trace schema.

Drag to turn

Crucible reads ticket and ERP exports, audit logs, model traffic, code history, test reports and policy documents. It maps them to one trace schema. Redaction occurs before storage.

$ crucible ingest my_pack
  • Redaction first. Crucible replaces each secret with a stable pseudonym.
  • Non-intrusive capture. A recording proxy observes live agents.
  • Repeatable ingestion. A second ingestion of a source yields identical records.
  • Probe tagging. Crucible tags lookups of answer sources and excludes them from scoring.
Expert feedback

Expert judgment from existing logs

Corrections, approvals and reverts become weighted evidence.

Drag to turn

Crucible extracts expert feedback from the records. It attributes each item to the step that it evaluates and weights it by how well it predicts later outcomes.

$ crucible signals my_pack
  • Typed signals. Each domain maps onto 13 shared signal types.
  • Last-writer attribution. Crucible attributes feedback to the last step that modified the object.
  • Learned reliability. Crucible down-weights unreliable signals.
  • Contrastive pairs. Each corrected error yields a pair of the erroneous step and its correction.
Workflow map

A model of the workflow

Crucible mines stages and milestones from recorded work.

Drag to turn

Crucible segments each record into steps and reconstructs the state after each step. It mines verifiable milestones from changes, test results and reviews. A tracker reports the progress of any agent.

$ crucible model my_pack
  • Replay validation. The reconstructed state must match the record.
  • Milestone criteria. Each milestone is executable and predictive of success.
  • Data-derived stages. An ordering must hold in at least 90% of records.
  • Quarantine. Crucible excludes records that do not replay.
Reward

Dense step-level reward with isolated verification

Step scores

Step-level reward

A dense progress signal that is robust to reward exploitation.

Drag to turn

Progress is the weighted fraction of milestones that the agent completed. A milestone counts only when its prerequisites hold. Each step receives the change in progress. Hard constraints and a cap keep partial completion below success.

reward  R = G · [ O·(1 + αp + βe) + κ·(1 − O)·Φ ]    κ ≤ 0.3
  • Potential-based shaping. Cycles yield zero net reward.
  • Hard constraints. A single violation yields zero reward.
  • Capped partial credit. Partial completion always scores below success.
  • Branch values. Crucible estimates them from restored snapshots.
Result checks

Isolated verification

Hidden checks that known reward-hacking attacks cannot defeat.

Drag to turn

The checks run in a separate container without network access. They trust only evidence that the agent cannot modify, and they compare outputs with hidden references. They ignore exit codes and self-reported claims.

  • Trusted evidence. The checks use only artifacts that the agent cannot forge.
  • Differential checks. Hidden references and fresh samples detect forged results.
  • Noise-aware timing. Crucible masks noisy performance runs instead of failing them.
  • Attack suite. Control runs demonstrate the effect of each defense.
Make tasks

Solution-first task synthesis with evidence-based admission

Task builder

Synthesis of frontier-hard tasks

Specialized roles work behind information barriers.

Drag to turn

Specialized roles transform work records into new worlds and tasks. The solution and the hidden checks exist before any solver attempts the task. Each role receives only its permitted inputs.

$ crucible forge my_pack
  • Solution first. The reference solution and checks precede every attempt.
  • Canary detection. A role that leaks the solution marker fails.
  • Grounded traps. Each trap derives from recorded expert feedback.
  • Calibrated difficulty. Crucible targets a training pass rate between 0.1 and 0.7.
Quality gate

An acceptance contract for every task

Eighteen executable checks precede admission to the task pool.

Drag to turn

The contract confirms that the reference solution passes and that trivial attempts fail. It also confirms that the checks detect injected defects, that no answer leaks and that the verifier resists attacks. No model decides a gate. Each new class of defect becomes a new check.

$ crucible accept my_pack
  • Cost ordering. Inexpensive checks run first, and human review runs last.
  • Mutation score of at least 0.9. The checks must detect injected defects.
  • Incremental regrading. An edit re-evaluates only the affected checks.
  • Growing registry. Each new detector re-evaluates all tasks.
Run and learn

Agent execution, asynchronous training and long-horizon context

Agent runs

Separation of infrastructure and policy faults

Repeated sampling, arbitrary policies and an attributed cause for each failure.

Drag to turn

Crucible evaluates each task with each policy over many samples. It uses budgets, retries and a resumable journal. It excludes infrastructure faults from all averages and scores policy faults.

  • Failure attribution. Crucible excludes infrastructure faults and scores policy faults.
  • Budget accounting. Crucible reserves budget before each attempt and settles it after the attempt.
  • Resumability. Crucible never repeats completed work.
  • Offline regrading. Crucible regrades a run from its artifacts without new rollouts.
Model training

Asynchronous RL on exact tokens

Rollout collection and policy updates proceed concurrently.

Drag to turn

Agents act in live worlds while the policy updates. Each token records the policy version that produced it. Crucible bounds staleness at admission, at batch selection and in the loss.

$ crucible train job.toml
  • Exact tokens. Crucible trains on the sampled tokens without retokenization.
  • Three placements. Training and inference share one GPU, share part of the GPUs or run on separate machines.
  • Off-policy correction. Crucible reweights each token according to its staleness.
  • Turn-level credit. Crucible maps step rewards onto the tokens of each turn.
Long tasks

Episodes of one million tokens

Compaction, checkpointing and recovery with exact reward accounting.

Drag to turn

A single episode can span thousands of steps. Near the context limit, the model writes its own summary and opens a new segment. The world checkpoints its state at fixed intervals, and an interrupted episode resumes from the last checkpoint.

  • Self-summarization. The model writes a summary at 80% of the context limit.
  • Segments. Each summary opens a new segment that Crucible trains.
  • Exact sums. The step rewards sum to the final reward.
  • Linear storage. Crucible stores only the new tokens of each step.
Memory agent

Context in a persistent kernel

A short prompt over a persistent memory.

Drag to turn

The task, the tools, each observation and each message are variables in a sandboxed kernel. The model reads them with code instead of holding them in its prompt. Crucible keeps earlier turns word for word, and the model can still search them.

  • Prompt as variables. Task, tools, observations, messages and history.
  • One step per call. Each world call is one world step.
  • Bounded prompt. The prompt stays short as the episode grows.
  • Exact restore. Crucible replays the kernel journal and verifies it.
Task repair

Self-repairing tasks

Planning, implementation, review and verification precede each commit.

Drag to turn

The memory agent also runs a loop that repairs and improves tasks. A separate model reviews each change, and the acceptance contract, not a model, makes the final decision.

  • Adversarial review. A second model searches for defects.
  • Objective verification. The acceptance contract decides.
  • Monotone checks. A change can only strengthen the checks.
  • Journaling. An interrupted loop resumes from its last state.
Measure and ship

Step-level evaluation, deterministic export and domain extension

Benchmarks

Step-level evaluation

Progress measures beyond binary success.

Drag to turn

Crucible benchmarks report rule violations, depth and speed of progress, regressions and cost. Fixed anchor items and newly generated items share one calibrated scale, which keeps versions comparable and limits contamination.

$ crucible bench run finance_ap --out runs
  • Coverage-aware averages. Masked samples never count.
  • Anchor and fresh items. Secret seeds generate the fresh items.
  • Shared difficulty scale. Crucible places models and items on one scale.
  • Paired tests. Crucible compares versions on identical items.
Replay and export

Deterministic replay and export

Each episode replays into identical reward and step files.

Drag to turn

Crucible normalizes a recorded episode into canonical actions and replays them in a fresh world. A single reward producer grades the replay. The reward and step files are identical on every replay and serve both training and audit.

$ crucible export --to canonical --pack finance_ap
  • Canonical actions. Crucible derives its own call identifiers.
  • Fresh replay. The actions execute in a new world.
  • Determinism. Every replay yields the same reward file.
  • Mask preservation. Crucible never writes a masked episode as zero.
Domain packs

Domain packs

A single manifest describes each domain, and the core remains unchanged.

Drag to turn

A pack contains all domain-specific components. These are sources, credit rules, generators, policies and fixtures. Crucible validates each pack at three levels before use.

$ crucible pack new my_pack --dir ./my_pack
$ crucible pack check ./my_pack --level semantic
  • Static validation. Crucible checks the manifest, license, layout and hooks.
  • Fixture validation. Each designed case receives its expected score.
  • Semantic validation. The reference solution reaches the maximum reward, and the untouched task does not.
  • Accounts payable. A three-way match with five fraud controls.

The label command converts workflow logs into scored traces and training data. The build command converts the same logs into accepted tasks, exports and a benchmark.

Quick start

        
The quick start needs no model, GPU or API key.

        
All steps run on a laptop CPU in about two minutes. Each command prints the next command.

      

      
# make a domain pack and check it at all levels
$ crucible pack new my_pack --dir ./my_pack
$ crucible pack check ./my_pack --level semantic

# turn logs into scored records and training data
$ crucible label --pack my_pack --out label

# turn logs into accepted tasks and a benchmark report
$ crucible build my_pack --out build

# run a real domain, accounts payable
$ crucible bench run finance_ap --out runs
