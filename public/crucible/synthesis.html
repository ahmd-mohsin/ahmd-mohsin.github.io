Task and environment synthesis

Task synthesis in ten modules

Crucible turns enterprise systems and code repositories into training tasks that carry proof of what they test. Ten modules do the work. Six of them make, break, judge, certify and place each task. Two of them run the regularised improvement loops. Two of them measure the pipeline and hold its rules. Select a module on the map to read what it does.

The modules

What each module does

01

The World

The environment the agent works in, and the source of truth about it.

Does

Runs a realistic system with its own tools, records and documents, and decides by execution what the correct outcome is.

Inside
  • World families. Enterprise systems such as accounts payable, receivables, insurance intake, leave and purchasing. Code repositories in several languages.
  • Tool interface. The same calls for every World, so the rest of the pipeline never depends on the domain.
  • Canonical state and diff. Every run ends in a state that can be compared exactly with another.
  • Executed truth. The World's rules, written as data, compute the correct decision for any state. For code, the reference version and its tests play this role.
  • Read sets. The records a decision depends on, found by changing one record at a time.
  • World repairs. A World that lacks a tool or a record view is repaired in its data, never in the pipeline's code.
Takes

A system's rules, records and documents, or a repository.

Gives

Tools, states and the correct outcome for any state.

02

Task builder

Makes a task from a decision the World already fixes.

Does

Starts from the answer and works backward. It finds an outcome the rules fix, builds the solution and the checks from it, and writes the instruction last.

Inside
  • Decision points. Candidate writes are executed to find outcomes the rules decide.
  • Reference program. The sequence of tool calls that reads the evidence and makes the correct change.
  • Checks. What the final state and the answer must show, including that the evidence was read before the change.
  • Instruction. Written last by a builder model. It names the kind of evidence and never the answer.
  • Difficulty targeting. Predicts difficulty from executed features before any student run and prefers decisions in the learning band.
  • Birth gates. Refuse a task that leaks, has a dead reference or contradicts itself.
  • Round trip. A solver from another family must reach the same decision from the instruction alone.
Takes

A World and a target skill.

Gives

A candidate task with its instruction, reference program and checks.

03

Falsification

Tries every known way to break the task.

Does

Runs probes that a sound task must handle. Each probe targets one named defect. A probe that succeeds is a counterexample.

Inside
  • Program mutants. Wrong versions of the solution must fail the checks. Small mutant spaces are run completely, and proofs cover whole classes of mutants.
  • Degenerate agents. Doing nothing, or doing something redundant, must fail.
  • Guess and skip programs. A program that guesses, or skips one required read, must fail.
  • Value tracing and leak checks. Every value the solution uses must come from the instruction or an observation, and the instruction must not leak the answer.
  • Twins, perturbation, scope and effects. The task must depend on the right entity, survive harmless changes, and check every change the decision needs.
  • Independent solvers. Models from families that built nothing in the task must solve it, on a ladder of increasing effort.
  • Attackers. Models try to pass without doing the work.
Takes

A candidate task.

Gives

Counterexamples and open suspects, each tied to a defect.

04

Judgement

Decides the cases a probe cannot decide alone.

Does

Settles whether a suspect is a real defect. Execution decides first. A model decides only when execution cannot, and only after it passes calibration.

Inside
  • Trusted grader. One small grading module that fails closed.
  • Executed truth first. The World's rules and read sets settle most suspects with no model.
  • Calibrated judges. A judge is trusted for one World only when its exact bounds on true and false rates clear a fixed bar. Irrelevant edits must also leave its verdict unchanged.
  • Outside families only. No model judges a trace that its own family made or a task that its family built. With no eligible judge, the answer is unknown.
Takes

Suspects and attempts.

Gives

Confirmed defects, cleared suspects, or unknown.

05

Certificate

Turns the evidence into a decision about the task.

Does

Keeps every counterexample, repairs what it can with typed fixes, and issues a certificate that bounds the defect rate. Only a certified task goes forward.

Inside
  • Counterexample archive. Every counterexample is kept and replayed against each new version.
  • Typed repairs. Each fix belongs to a known operator with a declared effect. The repair loop must converge and may not add defects.
  • Defect rate bound. Exact statistical bounds give certified, provisional, on hold or rejected.
  • Hint tier. A task that an independent solver passes only with a structural hint is labelled as such and never counted as certified.
Takes

Counterexamples, verdicts and statistics.

Gives

A certificate and a status for each task version.

06

Student probe

Places a proven task by difficulty and reads how the student fails.

Does

Runs the student on the certified task several times. It labels each success and each failure as intended or unintended and places the task.

Inside
  • Probe rollouts. A sequential test with looks after 4, 8, 12 and 16 attempts.
  • Outcome classes. A failure from a real skill gap is intended. A pass by a shortcut, or a failure from a defect, is not.
  • Learning band. A task is kept when the student succeeds between 10 and 60 percent of the time.
  • Placement. Keep, reserve, hold or drop. Kept tasks enter the training pool.
Takes

A certified task.

Gives

A placement, and unintended outcomes for Loop 1.

07

Loop 1 control

Task improvement while the task is made.

Does

Takes each unintended outcome or failed proof, finds the step and the cause, and chooses a typed move. It then proves the whole task again. It also lifts lessons into the builder.

Inside
  • Attribution. The first point of failure in the trace, the record involved and a typed cause.
  • Typed moves. Repair, relabel the skill, keep or reserve. A real skill gap is never repaired.
  • Lessons. Recurring repairs become rules for the builder, through a gate with held-out evidence.
Its seven guards
  • Success needs the evidence.
  • A real skill gap is an intended failure.
  • No model judges its own work.
  • No repair makes the task easier, and held-out tasks never change.
  • Every repair proves the whole task again.
  • The pass rate places a task and never admits one.
  • Lessons pass a gate before they change the builder.
08

Loop 2

In development

Data improvement after the student trains.

Does

Post-trains the student on the kept pool and evaluates it on sealed benchmarks. Coarse scores per skill show which skills the data teaches poorly, and the builder changes what it makes.

Inside
  • Sealed evaluator. Runs and scores the benchmarks inside a boundary.
  • Coarse scorecard. Rounded rates per skill and per failure type, with added noise and a fixed query budget.
  • Change menu. Reweight a skill, move its difficulty, change its systems, or add a lesson from Crucible's own traces.
  • Gate. A change counts only when it also helps on Crucible's own held-out tasks.
Its six guards
  • Benchmark items never leave the boundary.
  • Only coarse scores cross.
  • Signals name skills, never items.
  • A change must also help on held-out tasks.
  • A vault test runs once per release and never feeds the loop.
  • New tasks pass Loop 1 and an overlap screen.
09

Measurement

Measures the pipeline itself, not only its tasks.

Does

Checks that every module works as claimed, with numbers that can be compared from one version to the next.

Inside
  • Planted defects. Three sets of tasks with one known defect each give recall and false alarms per falsifier. One set stays locked.
  • Residual defect estimate. A bound on how many defects remain in the kept pool.
  • Paired live rounds. The full pipeline runs live on a fixed set of cells, with and without the newest mechanisms.
  • Trace error analysis. Every model's traces are kept, read and sorted into failure types, each with a code check that finds the first point of failure.
10

Rules and records

Holds the decisions every module follows.

Does

Turns every design decision into a versioned rule and keeps a tamper-evident record of each change. Each result names the rules it was made under.

Inside
  • Decisions as rules. Each rule has parameters, a reason and the code that enforces it. Rules change only through recorded amendments.
  • Stale results. When a rule changes, every stored certificate, judge example and kept task that the rule touches is decided again.
  • Role separation. Builders, checkers and the student come from separate model families.
  • Records. Every run records its spend, its model calls and the rule version it used.

Modules 1 to 6 make a task and prove it. Module 7 repairs a single task and module 8 improves the whole data set. Modules 9 and 10 keep the pipeline measurable and accountable. A kept task therefore carries a certificate, a placement and the rule version behind both.
